La Pokédex cobra vida con JavaScript

Apuntes de la clase en la que el proyecto deja de tener los datos escritos a mano en el HTML y empieza a funcionar: la lista de Pokémon se genera sola, el buscador filtra de verdad y una sola página de detalle sirve para todos.

Este documento reúne los conceptos y lo que conviene recordar de cada tema. Comienza con un repaso de lo visto en las clases de JavaScript y continúa con los módulos y el DOM, que son los temas nuevos. El código se escribe en conjunto durante la sesión; aquí no se incluye, para que sirva como material de repaso y consulta.

Bloque 1

Fundamentos de JavaScript

Repaso de lo visto en las clases anteriores, más las piezas que se suman en esta sesión.

1

Funciones y funciones flecha

Repaso

Una función es un bloque de código con nombre que recibe datos de entrada, hace algo y devuelve un resultado. En JavaScript las funciones son valores: pueden guardarse en una variable, pasarse como argumento a otra función o devolverse desde una función.

La función flecha es una forma breve de escribirlas, muy usada cuando se entrega una función a otra, como ocurre con los métodos de los arreglos. Una función que se pasa a otra para que esta la ejecute se llama callback.

Conviene recordar

  • función recibe datos, hace algo y devuelve un resultado.
  • función como valor se guarda, se pasa y se devuelve.
  • callback una función que se entrega a otra para que la ejecute.
2

filter, map y reduce

Repaso

Son tres métodos de los arreglos que evitan escribir ciclos a mano. filter recorre el arreglo y conserva solo los elementos que cumplen una condición; cambia cuántos hay. map transforma cada elemento y devuelve uno nuevo por cada uno; cambia qué hay. reduce recorre el arreglo acumulando un único resultado final, como una suma o un máximo.

Los tres devuelven información sin modificar el arreglo original, y pueden encadenarse: filtrar primero y transformar después. Son la base para construir la lista y los filtros de la Pokédex.

Conviene recordar

  • filter conserva los que cumplen una condición.
  • map transforma cada elemento.
  • reduce combina todo en un solo valor.
3

Closures y ámbito

Repaso

Cada función tiene su propio ámbito: el conjunto de variables que puede ver. Un closure ocurre cuando una función interna sigue teniendo acceso a las variables de la función que la creó, incluso después de que esta terminó. Esas variables quedan conservadas y no son accesibles desde afuera.

Es la forma de guardar información privada, por ejemplo un contador que solo cambia a través de la función que lo expone. Es también la idea que, dentro de las clases, se formaliza con los campos privados.

Conviene recordar

  • ámbito las variables que una función alcanza a ver.
  • closure una función que recuerda las variables donde nació.
  • encapsular guardar datos que no se tocan desde afuera.
4

Clases y prototipos

Repaso

Una clase es una plantilla para crear objetos con la misma forma y el mismo comportamiento. Evita repetir las propiedades y los métodos en cada objeto. Por debajo, JavaScript comparte los métodos a través de un mecanismo llamado prototipo: cuando una propiedad no está en el objeto, se busca en su prototipo, y así sucesivamente a lo largo de una cadena.

Con una clase se definen los datos en el constructor y los métodos una sola vez para todos los objetos. Una subclase puede heredar de otra y agregar lo propio.

Conviene recordar

  • clase plantilla para crear objetos iguales en forma.
  • prototipo dónde se comparten los métodos entre objetos.
  • herencia una clase que reutiliza y amplía otra.
5

Getters y setters

Un getter es un método que se usa como si fuera una propiedad: se lee sin paréntesis, pero por dentro ejecuta código. Un setter es su contraparte al asignar un valor: en lugar de guardarlo tal cual, el valor pasa por un método que puede revisarlo o ajustarlo primero.

Su utilidad es el control. Por ejemplo, la vida de un Pokémon puede quedar siempre dentro de un rango válido (ni negativa, ni mayor al máximo), sin importar qué valor intente asignarle quien usa el objeto. La forma de usarlo desde afuera no cambia; la validación ocurre de manera interna.

Conviene recordar

  • getter leer un dato que en realidad se calcula o se protege.
  • setter validar o ajustar un valor en el momento de asignarlo.
  • campo privado (#) dato interno que solo se toca desde dentro de la clase; obliga a pasar por el setter.
6

Máquinas de estados

Una máquina de estados describe algo que siempre se encuentra en una de varias situaciones posibles —sus estados— y define qué acciones se permiten en cada una. Cualquier acción que no esté permitida en el estado actual se rechaza.

La comparación habitual es un semáforo: está en verde, amarillo o rojo, y no puede pasar de rojo a amarillo. Toda la lógica vive en una tabla de transiciones que indica, para cada estado, a qué estado lleva cada acción válida. Su ventaja es evitar situaciones imposibles y reportar el error de inmediato, en vez de arrastrar un fallo silencioso. Es la base del flujo de una partida en el proyecto Arcade.

Conviene recordar

  • estado la situación actual del sistema.
  • transición el paso de un estado a otro ante una acción válida.
  • tabla de transiciones el registro de qué acción lleva a qué estado.

Bloque 2

Módulos de ES6

Cómo repartir el código en varios archivos que se comunican entre sí.

7

Modularizar el código

Modularizar es dividir el programa en varios archivos, cada uno responsable de una tarea. Cada módulo decide qué comparte con los demás; lo que no comparte queda privado de ese archivo.

Existen dos estilos por razones históricas. CommonJS es el sistema clásico de Node. Los módulos de ES6, incorporados al lenguaje en 2015, son la forma actual y funcionan igual en el navegador y en Node. En el curso se usa el estilo de ES6; el otro se menciona solo para reconocerlo en código existente.

Conviene recordar

  • módulo un archivo con una responsabilidad clara.
  • CommonJS el estilo antiguo de Node (require).
  • ES6 el estilo moderno y universal (import / export).
8

Exportar e importar

Un módulo comparte lo que quiera marcándolo para exportar: una constante, una función, una clase. Desde otro archivo, se trae lo necesario con importar, nombrando exactamente lo que se quiere. Lo que no se importa, no entra.

La referencia al otro archivo es una ruta: un punto y una barra indican "en la misma carpeta", y en el navegador la extensión del archivo es obligatoria.

Conviene recordar

  • export ofrecer algo al resto del proyecto.
  • import { … } traer símbolos por su nombre.
  • ruta relativa dónde está el archivo, con extensión incluida.
9

Otras formas de exportar e importar

Además de la forma con nombre, hay variantes que se ven con frecuencia. La exportación por defecto marca el elemento principal de un archivo y se importa con el nombre que se prefiera. El alias permite renombrar algo al importarlo para evitar choques de nombres. Y es posible traer todo un módulo agrupado bajo un solo nombre.

Reconocer estas variantes evita confusiones al leer código ajeno, aunque en el día a día suele preferirse la exportación con nombre por ser más explícita.

Conviene recordar

  • export default el elemento principal del archivo.
  • as renombrar al importar.
  • * as nombre traer todo el módulo agrupado.
10

Módulos en el navegador

Para que el navegador entienda las importaciones, el script se declara como módulo. Al hacerlo, el archivo puede usar import y export, espera a que la página esté lista antes de ejecutarse, corre con reglas más estrictas y mantiene sus variables sin contaminar el ámbito global.

Existe una limitación histórica: cuando la página se sirve en el formato estricto XHTML, el motor de Safari no ejecutaba los módulos escritos directamente en el documento. En el HTML normal, que es lo habitual, los módulos funcionan en todos los navegadores.

Conviene recordar

  • script de módulo habilita import / export en el navegador.
  • modo estricto reglas más seguras de forma automática.
  • ámbito propio las variables no se vuelven globales.
11

Política del mismo origen

Al abrir un archivo con doble clic, su dirección no corresponde a un servidor y los módulos no cargan: el navegador aplica la política del mismo origen, una regla de seguridad que solo permite pedir recursos que provengan del mismo lugar.

La solución es servir la carpeta mediante un servidor local, aunque sea en la propia computadora. Herramientas como Live Server cumplen esta función: con ellas, todos los archivos comparten el mismo origen y los módulos cargan sin problema.

Conviene recordar

  • política del mismo origen regla de seguridad del navegador.
  • servidor local necesario para que los módulos carguen.
  • Live Server la forma práctica de servir el proyecto en clase.
12

XHTML en WebKit

Opcional

Este punto aplica únicamente cuando el proyecto se sirve en formato XHTML y se desea probar en Safari, donde los módulos no se ejecutaban. La solución que plantea el curso es ofrecer el mismo contenido también como HTML normal mediante un enlace simbólico: una referencia del sistema de archivos que funciona como un acceso directo, de modo que un solo archivo queda disponible bajo dos nombres.

Es un recurso para un caso muy particular. Con HTML normal no hace falta.

Conviene recordar

  • enlace simbólico un archivo accesible bajo dos nombres, sin duplicarlo.
  • caso de borde solo relevante con XHTML y Safari.
13

La Pokédex en módulos

Con todo lo anterior, el proyecto se reorganiza. Los datos dejan de estar repartidos en el HTML y pasan a un módulo único que actúa como la fuente de verdad. Las páginas de lista y de detalle leen de ese mismo módulo.

El beneficio es concreto: agregar o cambiar un Pokémon se hace en un solo archivo, y ambas páginas se actualizan en consecuencia. Las dependencias fluyen en una sola dirección, de lo general a lo específico, lo que mantiene el código ordenado.

Conviene recordar

  • fuente de verdad un único lugar con los datos.
  • separar datos y lógica cambiar datos sin tocar el código.
  • dependencias qué archivo necesita a cuál, en una sola dirección.

Bloque 3

El DOM

Cómo JavaScript lee y modifica la página para que la Pokédex funcione.

14

El DOM y los nodos

El DOM (Document Object Model) es la página vista como un conjunto de objetos que JavaScript puede leer y modificar. Cuando el navegador interpreta el HTML, construye un árbol en el que cada etiqueta, cada texto y cada comentario es un nodo.

El punto de partida para trabajar es obtener un nodo existente —por ejemplo, el contenedor de la lista, que al inicio está vacío— y a partir de él agregar o cambiar contenido.

Conviene recordar

  • DOM la página como objetos manipulables.
  • nodo cada pieza del árbol de la página.
  • seleccionar obtener un elemento por su clase o su id.
15

Crear elementos

Construir contenido desde JavaScript sigue tres pasos: crear un elemento nuevo, configurarlo (su clase, su texto, sus atributos como la dirección o la imagen) e insertarlo en la página, momento en el que aparece en pantalla.

La tarjeta de cada Pokémon se arma así, con la misma estructura y las mismas clases que antes estaban escritas a mano, de modo que los estilos siguen aplicando sin cambios. Un detalle clave: el enlace de cada tarjeta lleva el identificador del Pokémon en su dirección, lo que permite usar una sola página de detalle.

Conviene recordar

  • crear generar un elemento nuevo en memoria.
  • configurar asignarle clase, texto y atributos.
  • insertar colgarlo en la página para que se vea.
  • texto seguro el texto plano no interpreta etiquetas.
16

Generar la lista completa

Con la tarjeta resuelta, generar todas es recorrer la lista de datos y crear una tarjeta por cada Pokémon. Antes de dibujar, el contenedor se vacía, para que las tarjetas nuevas no se sumen a las anteriores.

Este es el objetivo central de la clase: los datos ya no están escritos en el HTML, sino que la lista se construye a partir del módulo de datos. La función que dibuja recibe cuáles Pokémon mostrar, lo que deja todo listo para el buscador.

Conviene recordar

  • recorrer pasar por cada elemento de la lista.
  • vaciar antes de dibujar evita contenido duplicado.
  • dibujar con un parámetro mostrar la lista que se le indique.
17

Filtrar y buscar

El buscador conecta el formulario con el código a través de eventos: uno responde al enviar el formulario y otro filtra en vivo mientras se escribe o se cambia una opción. Al enviar, se evita que la página se recargue, de modo que el filtrado ocurre sin salir de ella.

El proceso lee los criterios del formulario, conserva solo los Pokémon que cumplen con todos y vuelve a dibujar la lista resultante. Un detalle práctico: al comparar texto conviene ignorar las tildes, para que "eléctrico" y "electrico" se consideren iguales.

Conviene recordar

  • evento código que responde a una acción de la persona.
  • evitar la recarga filtrar sin abandonar la página.
  • filtrar conservar solo lo que cumple los criterios.
18

innerHTML y outerHTML

Para bloques grandes de contenido, en lugar de crear elemento por elemento, resulta cómodo escribir el HTML como texto y dejar que el navegador lo construya. innerHTML representa el contenido interior de un elemento; outerHTML incluye además la propia etiqueta.

Hay una advertencia de seguridad importante: usar esta técnica con texto proporcionado por una persona usuaria es riesgoso, porque podría inyectar código. Es seguro únicamente cuando el contenido proviene de datos propios y confiables.

Conviene recordar

  • innerHTML el contenido interior de un elemento.
  • outerHTML el elemento completo, con su etiqueta.
  • seguridad no usarlo con texto que teclee un usuario.
19

Una sola ficha para todos

La página de detalle deja de existir en diez copias casi idénticas. Queda una sola, y el Pokémon que debe mostrar viaja en la dirección, en la parte posterior al signo de interrogación, conocida como query string.

El código lee ese identificador, busca el Pokémon correspondiente y arma la ficha. Si el identificador no existe, muestra un mensaje en lugar de una página rota. Es la misma idea de la dirección con parámetros que ya se usó para filtrar, ahora aplicada a elegir el contenido.

Conviene recordar

  • query string los datos que van en la dirección tras el "?".
  • leer el parámetro obtener el identificador de la dirección.
  • caso no encontrado mostrar un mensaje en vez de fallar.
20

Nodos y elementos

Opcional

Para cerrar, una distinción que explica algunos comportamientos al depurar. Un nodo es cualquier pieza del árbol, incluidos los fragmentos de texto. Un elemento es un nodo que además es una etiqueta. Todo elemento es un nodo, pero no todo nodo es un elemento.

Por eso existen dos formas de recorrer los hijos de un contenedor: una incluye también los fragmentos de texto, y otra se limita a las etiquetas. En la práctica, casi siempre interesa la segunda.

Conviene recordar

  • nodo cualquier pieza del árbol (texto, comentario, etiqueta).
  • elemento un nodo que es una etiqueta.
  • recorrer hijos normalmente interesan solo los elementos.
